4. CONEXION A OLLAMA COMPARTIDO (M3)
--------------------------------------------------------------------------------
En docker-compose.template.yml de cada solucion custom:
  services:
    api:
      extra_hosts:
        - "host.docker.internal:host-gateway"
      environment:
        - OLLAMA_BASE_URL=http://host.docker.internal:11434
PROHIBIDO modificar o conectar redes al contenedor aria-ollama.
La fabrica (factory-api) NO necesita Ollama en su MVP.

7. POLITICAS — CONTENIDO MINIMO (se conservan las 5 + 1 nueva)
--------------------------------------------------------------------------------
code_agent_policy.yaml
  read_allowed:  [factory/**, app/** (solo lectura), .claude/skills/**]
  write_allowed: [factory/workspaces/<project_id>/** UNICAMENTE]
  forbidden:     [app/, docker-compose.yml, Dockerfile, .env, data/chroma,
                  data/audit_logs, backups/, contenedores aria-*, hotelbot-*]
  requires_human_approval: [commit, release, deploy, crear agente nuevo,
                            exponer puerto, borrar workspace]
  mandatory_validations: [quality_gate_runner antes de proponer release]
  enforcement: claude_bridge genera CLAUDE.md + .claude/settings.json
               (deny rules) desde esta politica. (M6)

docker_policy.yaml
  ports: segun registry/ports.yaml; container_names: <project_id>_<servicio>;
  red propia por proyecto: <project_id>_net; volumenes propios por proyecto;
  ollama: compartido via host-gateway; validacion: docker compose config
  obligatoria antes de cualquier up.

agent_creation_policy.yaml
  (criterios del prompt original se conservan integros: existente si cabe
  100%; perfil si base cubre 70-80%; nuevo si dominio nuevo/corpus propio/
  reglas propias/salida distinta). Requisitos minimos de agente nuevo:
  agent_id, nombre, descripcion, system_prompt, coleccion RAG >= 60 chunks,
  reglas asociadas, >= 5 preguntas de prueba con criterios de aceptacion,
  entrada en manifest y en registry/agents_catalog.yaml, evidencia.

approval_policy.yaml
  acciones que exigen Capa 9: aprobar diseño, crear agente nuevo, exponer
  puerto, release, deploy. Formato: approval.json
  {action, project_id, version, approved_by, approved_at, base_commit,
   gates_report_hash}. Registro espejo en audit JSONL. Deploy bloqueado
  sin approval.status=approved.

security_policy.yaml
  - API key por solucion: openssl rand -hex 16, solo en .env
  - .env en .gitignore (gate verifica)
  - gate: grep de la key en frontend custom debe dar vacio
  - no exponer puertos fuera de rangos del registry
  - no borrar workspaces sin backup tar.gz previo en backups/factory/
  - deuda tecnica registrada: key hardcodeada en UI del base (corregir solo
    en iteracion autorizada del base, NO desde la fabrica)

resource_policy.yaml  → ver seccion 5.

8. CLAUDE CODE BRIDGE — TASK PACKAGE (M6/M7)
--------------------------------------------------------------------------------
Por cada tarea, claude_bridge.py genera en el workspace:
  workspace/<project_id>/
    ├── CLAUDE.md            # contexto: arquitectura, restricciones duras,
    │                          rutas permitidas/prohibidas, obligacion de
    │                          diff y de no commitear sin aprobacion
    ├── .claude/settings.json# permisos deny fuera del workspace y de
    │                          comandos peligrosos
    ├── task.md              # requerimiento + alcance + criterios de
    │                          aceptacion + pruebas obligatorias + formato
    │                          de reporte
    └── (codigo exportado del tag base + archivos generados)

MODO A (inicial): Cesar ejecuta  cd workspace && claude  y pega/refiere task.md.
MODO B (futuro):  claude -p "$(cat task.md)" --output-format json, solo tras
                  validar el Modo A en al menos 1 proyecto piloto completo.

9. QUALITY GATES (14, formalizados como script)
--------------------------------------------------------------------------------
quality_gate_runner.py ejecuta y reporta JSON:
 G01 docker compose config (sintaxis OK)
 G02 puertos libres y registrados (port_registry + ss -tlnp)
 G03 /health OK de la solucion
 G04 /api/v1/knowledge/stats responde
 G05 min_chunks_per_collection >= 60 por coleccion del manifest
 G06 routing de agentes correcto (detect_agent con preguntas de prueba)
 G07 preguntas base heredadas: respuestas validas
 G08 preguntas nuevas por agente/perfil creado: criterios de aceptacion
 G09 /api/v1/audit/verify OK (hash chain de la solucion)
 G10 UI carga (HTTP 200 en /)
 G11 API key NO presente en frontend (grep vacio)
 G12 git status limpio en workspace (todo registrado)
 G13 git diff presentado y archivado en el reporte
 G14 approval.json presente y status=approved (solo para deploy)
Reporte: factory/releases/<id>/vX.Y.Z/quality_gates_report.json
+ hash del reporte registrado en factory_audit.jsonl.
