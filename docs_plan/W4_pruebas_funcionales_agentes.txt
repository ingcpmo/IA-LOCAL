============================================================
W4 — CONSOLA DE PRUEBAS FUNCIONALES POR AGENTE
GMP AI Factory · Mission Control · Post W3
============================================================

OBJETIVO
  Convertir Mission Control de visor de evidencia a consola de operación:
  permitir PROBAR cada agente desde el browser contra el deployment real,
  ver qué respondió, si pasó o falló, qué endpoint usó, y dejar evidencia
  auditada SOLO cuando se ejecuta una prueba explícita.

PRINCIPIO ARQUITECTÓNICO CENTRAL
  "Probar un agente" = enviar un CASO DE PRUEBA CONTROLADO a su endpoint
  funcional real del deployment (ej. POST http://localhost:8102/oos/records)
  y evaluar la respuesta contra un resultado esperado.

  Separación estricta (regla U5):
    - Ver catálogo / ver resultados previos = READER (GET, no audita)
    - Ejecutar una prueba                   = EXECUTOR (POST, audita)
  La evidencia se escribe SOLO al pulsar "Probar", nunca al abrir la sección.

REGLAS DURAS
  - No generar código nuevo de misión. No headless. No deploy. No Docker nuevo.
  - No tocar app/, .env base, docker-compose base, data/, backups/, aria-*, hotelbot-*.
  - Casos de prueba SOLO desde catálogo curado (no texto libre que permita
    inyectar datos productivos o lotes reales).
  - Datos de prueba 100% SINTÉTICOS (sample_id ficticio, sin PII).
  - Las pruebas corren contra el deployment de la misión (su puerto propio),
    NUNCA contra el producto base 8000 ni contra otra misión.
  - Timeout por prueba: 15s. Si el endpoint no responde → FAIL claro, no cuelga.
  - *** NO COMMIT SIN APROBACIÓN EXPLÍCITA DE CESAR ***

#   → lee factory/test_results/{project_id}.jsonl
#   → devuelve resultados de pruebas ya ejecutadas (read-only).

# EXECUTOR (audita) — ejecuta UN caso de prueba:
# POST /api/v1/layer9/missions/{project_id}/test/run
#   Body: {"test_id": "oos_create_out_of_spec", "run_by": "Cesar"}
#   Flujo:
#     1) Validar run_by no genérico (human/agent/system → 422)
#     2) Buscar test_id en el catálogo curado (404 si no existe)
#     3) Verificar deployment activo y health OK (409 si no está vivo)
#     4) Construir request al endpoint del deployment (base + endpoint)
#        - SOLO desde el catálogo. El usuario NO envía payload arbitrario.
#        - timeout 15s
#     5) Ejecutar la llamada HTTP real al deployment
#     6) Evaluar aserción (status_code + json_path + equals)
#     7) Resultado: PASS / FAIL / ERROR (con detalle)
#     8) Persistir en factory/test_results/{project_id}.jsonl:
#        {test_id, agent_id, endpoint, payload, response_status,
#         response_excerpt, assertion, result, run_by, run_at, latency_ms}
#     9) AUDITAR evento agent_functional_test_executed con:
#        {project_id, test_id, agent_id, result, run_by,
#         decision_origin: "human_confirmed"}
#     10) Devolver el resultado completo al browser

# EXECUTOR (audita) — ejecuta toda la suite de un agente:
# POST /api/v1/layer9/missions/{project_id}/test/run-suite
#   Body: {"agent_id": "oos_workflow_agent", "run_by": "Cesar"}
#   → ejecuta todos los test del agente en secuencia
#   → un solo evento de auditoría agent_suite_tested con resumen N/M PASS
#   → NO ejecuta si deployment no está vivo

# Reglas de seguridad del executor:
#   - El payload SIEMPRE viene del catálogo, NUNCA del body del request.
#     El body solo trae test_id + run_by. Esto impide inyección de datos.
#   - El endpoint destino SIEMPRE es del deployment de ESA misión (su puerto).
#     Validar que el puerto pertenece a la misión (registry/ports.yaml).
#   - NUNCA permitir base_url arbitraria (no SSRF).
#   - Sanitizar response_excerpt (máx 2 KB, sin volcar secretos si los hubiera).
